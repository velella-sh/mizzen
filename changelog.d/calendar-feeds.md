- **Calendar feeds from data.** The site config takes `calendars`: a map of name to `{ collection, where, events, reminders, groupBy, limit }`. Each event names a date field of the collection (and an optional end field for a run of days) and a title template; the config rejects an unknown collection, a field the collection does not list under `dates`, an empty `events` list, and a reminder that is not a whole number of days. A site without the key is unchanged.
- **Calendar files.** The new `calendars` output writes `calendars/<name>.ics` (RFC 5545, all-day events, CRLF line ends, lines folded at 75 octets without splitting a character) and, with `groupBy`, `calendars/<name>/<group>.ics`. Event ids come from the collection, record id, event name, and site host, and stamps from the record's `updated` field, then the snapshot date, then the reference date, never from the build clock or a page URL, so two builds write the same bytes. `reminders` (`30d`, `7d`) write one `VALARM` each; an empty calendar writes no file and is reported.
- **Add to calendar.** The `record-calendar` output writes one `calendar.ics` beside each record page with that record's events, and `LayoutProps.record.calendar` hands its address to the theme; a record with no events, or a collection with no calendar, gets neither.
- **Calendars in the head and in `llms.txt`.** A record page that has events in a calendar writes `<link rel="alternate" type="text/calendar">` for it, `LayoutProps.record.calendars` hands the theme each calendar's `https` and `webcal` address, and `llms.txt` lists each written calendar under `Calendars`. A page that is not in a calendar links none.
