- **Scale for thousands of pages.** `fixtures/data-large/generate.ts` writes a seeded data site of any size (three collections, references, two lists, one feed), and `scripts/bench-data.ts` measures cold, warm, and one-record builds.
- **Time and memory budgets in CI.** `bench/budget.json` holds a budget for each of the six measurements, and a `data benchmark` CI job fails when one is passed, printing every measurement next to its budget in the job summary.
- **Faster hreflang and sitemap on large sites.** The language groups of a site are computed once instead of once per page.
- **Record nodes in the dependency graph.** Every record of a collection a build reads is a node with a hash of its id and fields, with edges from its page, from its template, and (through a collection node) from every list; `changedRecords` compares record hashes, not file hashes.
- The invalidation plan covers data sites: a changed record rebuilds its page and the lists of its collection, a changed template rebuilds every page of its collection, and a changed schema, lock file, or collection config reads the whole collection again. The plan names the collections whose feeds and indexes are affected, and the records that moved.
- **Record-keyed render cache.** A record page is cached under its own record's hash and the hashes of the records it references, and the render settings key holds the site's shape (every page URL and title, the navigation, each collection's record ids) instead of the collection's bytes. Editing one field of one record re-renders that page alone, and entries of edited or removed records are pruned. A layout that reads another record's fields without being a list page is outside that contract.
- A build lets go of each page's render and each output file as it is written, instead of holding all of them at once; the bytes and their order are unchanged, and a test bounds peak memory growth per record.
- **Search indexing is measured.** The data benchmark has a `search` case that times the search output alone and reports the index size, with budgets for both. Record pages are indexed from the model's HTML, never from the built files, and every page keeps its fragment: 10,000 records index in about two seconds into a 3.7 MB index.
- **`dev` and `watch` say how much a rebuild reused.** With the render cache on, a rebuild line ends with `(1 page rendered, 3030 reused)`, and the build result carries `renderedPages` and `cachedPages`; changing one record renders that page alone.
- **A performance page generated from the benchmark.** `docs/performance.md` and the docs site's `performance` page carry a table written by `scripts/perf-doc.ts` from `bench/last-run.json`, next to the CI budgets and the cases that make a build start over; a test fails when the page and the JSON disagree.
